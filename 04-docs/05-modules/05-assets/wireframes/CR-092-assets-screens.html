The export is broken on the deployed stack, and it is one missing line of docker-compose.yml

Reported from smartbillhub.bynry.com on 2026-09-11 (Ottumwa Water Works, v2.234.17): the export accepts, the notice says “Your export is ready. Download the CSV”, and the browser saves file.json and says “File wasn't available on site.”

The filename is the diagnosis. The link is an <a download> pointing at /api/exports/{job_id}/file — a URL whose last segment is file, with no extension, because the real name arrives in Content-Disposition. When the response is a JSON error instead of a CSV, Chrome names the download from the URL plus the MIME type and gets file.json. So the request reached Django and Django refused it: the SPA proxy never falls back to index.html for /api/*, which rules out an HTML body.

Why Django refuses it. export_file answers one plain 404 for five different noes, and the one that fires here is the last: artifact_within_dir() ends with candidate.is_file(), and the file is not on that container.

POST /exports → backend container → job accepted, 202 celery worker → runs the body → writes /app/var/artifacts/ottumwa_….csv ← HERE GET /exports/{id}/file → backend container → looks in /app/var/artifacts ← EMPTY → is_file() False → 404 JSON → file.json

The two halves are each written down and nobody added them up. 06-backend/.env.example:173 sets JOBS_EAGER=false, so the job body runs on the celery container and never on the web one. And docker-compose.yml mounts no volume on any service — there is no top-level volumes: key at all — so /app/var/artifacts is private container disk in six separate containers. The compose file even reasons about the risk and reaches the wrong conclusion: “they survive a restart, and they do not survive docker compose down or a rebuild … today's only job kind is a CSV export fetched within seconds, so that is a real but small consequence.” That sentence assumes the writer and the reader are the same container. With JOBS_EAGER=false they never are, so it is not small and it is not occasional — every export fails, every time.

⚠ And the runbook's mitigation is gated on a trigger that will not fire. §10.6 is open and correct about the mechanism — “an export written on replica A 404s when the download lands on replica B” — but it makes the shared volume “Required, not optional, the moment web desiredCount > 1.” The true condition is the moment JOBS_EAGER is false, which production sets by default, so the fix stays parked at one replica while the feature is broken.

Two more downloads break the same way and neither has been reported yet: the bill print set (celery-billing writes a ZIP through the same finish_artifact contract) and the audit-log export. All three register through register_export_kind and all three read from the same directory. Specification AST-B-20.

The rules this screen is built to

Fifteen rules for the detail view, minted here because no rule set in this repository covers a screen whose shape changes with the kind of thing it is showing. They are PROPOSED, not ratified — B14 is the authority and none of these has been put to the PO yet. The last column is the point: almost all of them are checkable by a machine, and none of them by a gate. Nothing in this repository reads rendered output — but vitest does, so these belong as component tests beside AssetDetail.test.tsx, not as a merge gate.

RuleWhat it saysHow it is checked
AST-R-01 One template, every kind. The detail view is one component. The tab set and the panel set vary; the structure, the order and the panel names never do. This restates the rule the code already states in its own words — “ONE template, EVERY kind — the tab SET is what varies, the structure never does” — and extends it from tabs to panels. Human review. A snapshot of panel order per kind makes drift visible.
AST-R-02 A panel or row a kind cannot have is ABSENT, not empty. Never draw a row of dashes for a fact the kind has no source for. The precedent is already in the product, on the Reads table: “a column of dashes on a meter that cannot export would read as measured nothing, which nobody did.” Machine. Render a device and assert the Measurement panel and its labels are absent from the DOM.
AST-R-03 Absence by KIND is silent; absence by DATA is stated. The two are different facts and the screen must not render them the same way. This kind has no register → the row is not drawn. This meter has no connection size recorded → the row IS drawn, with a dash, and where the absence has a consequence the consequence is named. The product already does the second half: “Not recorded — a rate ladder that prices by size cannot price this meter.” Machine. Two fixtures per contested row: the wrong kind (absent) and the right kind with a null (present, dashed).
AST-R-04 Measurement belongs to measuring kinds only. Multiplier, unit of measure, register digits and read method render on a meter and a sub-meter and nowhere else — the same reasoning that gives a plain device no Reads tab, applied one level down. Machine. Per-kind render test.
AST-R-05 Allocation belongs to sub-meters only. Allocation share, allocation rule and loss tolerance render on a sub-meter and on nothing else. A null share means metered, not allocated and is served as null — never as a zero, which would read as allocated nothing. Machine. Per-kind render test, plus one asserting a null share does not render 0%.
AST-R-06 Export capacity belongs to an exporting device only, and it is a capacity in kW, never money. BR-AST-025 keeps tariffs and credited dollars off this whole kind. Machine. Render test, plus the currency-symbol assertion BR-AST-025 already earns.
AST-R-07 Every kind names what it hangs off, and names it as a link. A sub-meter names its master; a behind-the-meter device names its linked meter; a master names the sub-meters on it. Today the master is plain text while parent_asset_id is served — a dead end with the id sitting right beside it. Machine. Assert an anchor, not a string, for each of the three.
AST-R-08 The tab set and the panel set are DERIVED, never written per screen. One function decides each from the asset, so a new kind changes that function and nothing else. assetDetailTabsFor() already does this for tabs; panels need its twin. Machine. A grep test: no tab id or panel id literal outside the two deciding functions.
AST-R-09 A fact is said once. The status is the pill; the number is the title; every other fact lives in exactly one panel. Where the header abbreviates a chain — 118 Bayou Bend Dr · Unit A · ACC-20194 — the panel carries it in full: that is a summary, not a repeat. The test for the difference: does the header carry the complete value? A pill does; an address line does not. This screen breaks the rule twice today — Parent and Last test date each render in two panels. Machine, and cheap. Assert every <dt> label appears at most once. It would have caught both.
AST-R-10 No database id is ever a visible value — B14 rule 31, inherited and restated because this screen carries five ids on the wire (id, service_point_id, premises_id, unit_id, parent_asset_id) and four of them exist to be link targets. A target is not a value. Machine, and cheap. Assert no rendered text matches a UUID.
AST-R-11 Panel order is fixed and does not vary by kind. Assignment · What's due · Measurement · Device · Cost & value · Lifecycle. A kind that skips a panel closes the gap; it never reorders. Somebody who learns the screen on a meter must not have to re-learn it on a device. Machine. Assert the rendered panel sequence is a subsequence of the canonical six.
AST-R-12 A panel label is at most two words, and names the question rather than the table it came from. PO instruction, 2026-09-11, verbatim: “I need label - maximum 2 words only panel label should be 2 words only”. Assignment, not Where it is and what it bills. Machine, and trivial. Word-count every panel label.
AST-R-13 Adding a kind is a four-line change. A new kind declares its tab set, its panel set, what it hangs off, and its Measurement rows — and touches nothing else. If a new kind needs an edit anywhere else in the detail view, the template has drifted and AST-R-01 has already been broken. This is the rule that keeps the other twelve true a year from now. Human review, at the moment a kind is added — which is the only moment it can be checked.
AST-R-14 A field's helper is one line — at most ten words — and never wraps. Not a style preference: a helper that wraps pushes its own input down, and in a two-to-a-row grid that leaves the two inputs of one row on different baselines. The alignment defect and the copy defect are the same defect. Measured across the assets module: 27 of 37 helper strings run over ten words, and the worst is 36 — “The size of the service connection this meter sits on. A rate ladder that prices by size uses it, so a wrong one changes the bill. Leave it blank if you do not know it yet.” B14 rule 32 already caps a screen's description budget and rule 33 caps a refusal at five or six words; a field helper had no cap at all. Machine, and trivial. Word-count every helper string in the catalogue. It needs no rendering — the copy is the defect.
AST-R-15 Two columns are two fields. Never one input holding both with a delimiter the person has to type. The product does this once — Manufacturer / model, with the help “One line; separate the two with a middle dot” — and it is the only field in the module that asks a human to do a parser's job. A model name containing the delimiter, or a person reaching for a slash instead, lands in the wrong column, and nothing on the screen says which half is which. Displaying them joined is fine; the detail view's single Manufacturer / model row is good density. The rule is about CAPTURE. Machine. Assert that no input's value is split or joined on a delimiter between the form and the payload.
AST-R-16 Every choice control names where its options come from, on the drawing itself. Four markers and nothing else: set a tenant-editable Settings list, named by its list code · tbl live rows from another table, named with its module · fix frozen in the source, with the count · none no list exists, or the product renders free text over a list that does. A drawn drop-down is a box with a word in it, and a picture cannot distinguish a row a utility can add this afternoon from a string that needs a release — so a coder reading the drawing alone guesses, and the guess is invisible once it is written. The marker travels ON the field rather than in a table beside it, because a table beside it is the thing that goes stale. The full map is Appendix L. Eye. Nothing mechanical can check this — the claim is about a list's PROVENANCE, which no gate in this repository can see. It is checked by reading Appendix L against the code the day a form is built, which is exactly when it is cheapest.

Why these are tests and not a gate. This repository's standing weakness is that no gate reads rendered output, which is why most B14 rules are ratified and unenforced and why nine defects were once found only by a human opening the running app. Ten of these thirteen are assertions about the DOM, and the component suite already renders this screen — so the enforcement that does not exist as a gate exists already as a test file. Two of them (AST-R-09 and AST-R-10) are three lines each and would have caught faults this document found by reading.

Interaction design — what a person can do here

Seven decisions, each one a change to what the screen does rather than to what it says. Six of the seven cost nothing on the server.

DecisionTodayProposed, and why
The account is a link Plain text — account_no · customer_name, rendered with no anchor. Link it. Premises and Unit are both links already, so the chain reads Premises → Unit → dead end, and the dead end is the money. The id is on the payload (billing_chain.account); nothing new is needed.
The master is a link Plain text — {asset.parent_asset_no}, no anchor, while parent_asset_id sits on the same payload. Link it. A sub-meter's master is the single most likely next click from a sub-meter, and the id needed to build the address is already in hand.
Edit per panel One Edit control for 23 fields. A person correcting a seal number opens a form holding every fact about the asset. A pencil on each panel, opening the edit form at that group. Twenty-three fields in one form is why nobody edits — and it is also why a mistyped field is hard to spot before saving. The form is already a page (screen 14), so it can carry an anchor.
What's due carries its action Dates in a list. A person reads Next due 06/15/2026, and then has to go and find the control that does something about it. Each overdue or approaching item carries the one control that resolves it — Annual test overdue 11 days → Raise work order →. It turns a reference panel into a working one, and it is the same destination BR-WRK-056 already names.
Absence names its consequence A dash, for every missing fact, whatever it costs. Where an absence has a consequence, say it. The product already does this once and it is the best sentence on the screen: “Not recorded — a rate ladder that prices by size cannot price this meter.” Apply the same treatment to the handful of others that matter and leave the rest as dashes — a screen where every dash carries a sentence is a screen nobody reads.
Status said once A pill in the header and row 21 of Specifications. The pill only. Saying it twice makes neither authoritative, and it is the cheapest of the three duplications this screen carries to remove.
The header earns its attention strip Nothing. A meter with a test eleven days overdue looks exactly like a healthy one until you scroll to the fifth panel. A strip that appears only when something needs doing, and is absent otherwise. Every fact it needs is already served — test_due, next_test, certification_due, warranty_covered, status. Silence when healthy costs nothing and is what makes the strip worth reading when it appears.

Asset edits — what each pencil opens

Six surfaces, one per editable panel on the Overview, plus the one state in which there are none. They cost nothing on the server: PATCH /assets/{id} validates a PARTIAL payload already — _validate_asset(data, partial=True) — so a form that sends only its own panel's fields is exactly the shape the endpoint expects.

Page or dialog — the rule, so it is checkable rather than taste

A PAGE when you are creating something, or when the change moves where the thing lives. A MODAL when you are correcting a value on something you are already looking at.

Add an asset, four stepsPage — creating.
Reassign · RetirePage — it moves where the asset lives: a service point is minted and a final read is taken.
Edit one asset (screen 14)Page — twenty-three fields, and the PO ruled it: “this should be form and not modal”.
A per-panel pencilModal — two to nine fields, and you are already looking at the value you are fixing. Sending somebody to a full page to correct a seal number loses their place on the screen they were reading.

The construction is identical either way: B14 rule 38 says the UI rules decide how a form is built, so R12's label → input → helper and R13's two-to-a-row grid apply to a dialog exactly as they apply to a page. Only the container changes.

One pencil on this screen can restate what a reading means. It is the only one, and that is by design.

Five fields are billing-affecting — multiplier · unit · net_metering · service · size_class — and BR-AST-012 makes a change to any of them apply FORWARD ONLY once reads exist: stored reads and issued invoices are never restated, and the response carries a forward_only_change warning.

⚠ So Connection size moves out of the Device panel and into Measurement, which is a change to the architecture agreed earlier in this document and is made for a reason rather than for tidiness: with it moved, all five sit in one panel, exactly one pencil on the screen can restate billing, and one confirmation covers it. Left in Device, two panels would each need the same warning and a person could meet it from either.

meter_type is explicitly not on that list — “it classifies the device; no rate, quantity or invoice line is derived from it, so re-tagging a meter restates nothing” — documented in the service rather than silently chosen, which is why the Device modal needs no confirmation at all.

AST-33

The button had to save something, and the product already knows where to put it

Both wizards now carry one exit and it is Save as draft — the five add steps and the three retire steps. The two it replaces were wrong on both: Save & exit wrote nothing at all — all six of its consumers are a bare navigate(…) — and Park asks what are you waiting on from nine reasons that belong to the customers' world, none of which is why a meter install or a removal stalls.

Where the draft goes is settled law, not a new decision. BR-SHL-048, ruled by the PO on 2026-08-26, in their own words: “Option A - Unitl move in executed, no records updates.” A half-finished wizard is a saved draft of a FORM, held in wizard_parks, and nothing it describes is touched until it commits. Five wizards run on this today; these are the sixth and seventh.

So the draft is a row with the status — a wizard_parks row IS a draft; existence is the status — and nothing else moves. On an add: the asset number is still only taken at the end, so an abandoned draft leaves no gap in the tenant's series, and no picker, KPI, rollup or parent-master list can show a half-made asset. On a retire: the asset goes on working — it stays in service, keeps collecting reads and keeps billing until the wizard is actually finished.

Retire differs from Add in exactly one place, and it is the resume

An add draft describes something that does not exist. A retire draft describes something that does — and BR-SHL-048 (a) stores the subject as copied values, never a foreign key, deliberately, so that a forgotten draft can never block a delete or hold a row still.

The consequence is real and is the whole of the difference: between saving and resuming, that asset can be reassigned, or retired by somebody else through the row action, or deleted. So resume re-reads the asset and checks it before drawing step 1, and a draft whose asset is already terminal says so and offers only Discard — BR-AST-030: retired is the end state, and there is no un-retire. The same re-check the wizard already does on open; it is being asked one more time, on a form that may be a week old.

Everything else is identical, which is the point of giving them the same treatment: one list, one resume, one discard, one constant in waiting_on.
