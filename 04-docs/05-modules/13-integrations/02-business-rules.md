**Numbering, and why it is not the offset the decision log expected.** The design document numbers its

nothing — and the collision the decision log describes is real only for the document's *existing-rules*

source finds the same id here) and the approved band `018`–`053` is completed by seventeen more:
the six principles `P1`–`P6` as `037`–`042`, and eleven rules `043`–`053` that carry the specification
cards the nineteen do not reach. The band and the count are exactly what the PO approved; only the
arithmetic inside it changed. Recorded in the decision log 2026-09-03.

**Ten of the seventeen existing rules bind this design without amendment**, and one is flagged with its
figure: `BR-INT-001` (the manifest's `disposition` is this rule made into data) · `002` (the endpoint set

## BR-INT-078 — CUSTOM APIs ON A CONNECTOR: THE KIND IS OURS, THE NAME IS THEIRS

> *"here Customer is giving custom URLs - when we read - and we will ahve to

**The business goal is REDUCING CUSTOMISATION WORK.** Every layer a customer can
point us at themselves is a release we do not have to cut. That is the measure
this rule is judged by, and it is why the closed Kind list is a constraint on
**US** rather than on them.

### ⚠ IT SUPERSEDES AN EARLIER, BROADER RULING, AND BOTH ARE KEPT

The Integration Blueprint ruled on **14 September** (p15 `CR-3`, p164): *"Can a
clerk rename an API we declared? **No.** 'no clark will not do it — we will do it
during initial configuration'. The set-up form lists APIs and does not edit them.
The disabled + Add an API control is removed."* The PO ruled that **too broad**
on 17 September. Both statements stand in the record, because a record of what
was ruled at a moment is evidence and editing it stops it being evidence.

**The distinction is the CONNECTOR, not the customer:**

* a **PROTOCOL READER** — our Esri connector knows how to query an ArcGIS layer
  and does not care WHICH layer — needs **no new code** for a customer's extra
  URL, so a clerk may add one;
* a connector whose **every API is bespoke** still falls under the old rule and
  offers nothing. Twenty-seven of twenty-eight are in this half today.

⚠ **The blueprint also banked its ruling's saving as *"no schema change"*,
observing that a clerk-owned name *"would need a per-connection field that does
not exist"*. That field now exists — `integration_api`, migration
`integrations/0014` — so the cost the blueprint named is paid knowingly.**

### The rule

**A clerk picks what SORT of call this is from a closed list WE ship, and gives
it their own name and their own URL. Nothing addable can lack code behind it.**
A genuinely new KIND of call is a **Runbook**, not a form field (PO: *"any every
custom APis for that customer - we wil ahve to write a code to exeucte business
logic for that - which is another issue that we have to handle - using
runbook"*) — a URL alone cannot express what to do with the answer.

**The list is closed MECHANICALLY and not by discipline:** a Kind is offered
only where this connector already declares the OPERATION that runs it

### The five rules, and each reason, because a rule without one gets simplified away

| # | Rule | Reason |
|---|---|---|
| 1 | **ONE Scheduled sync per connector**, counting ours and theirs together. A second is refused **at the form AND on the server**, in words a clerk reads | a sync **WRITES**. Two pointed at two layers both update the same premises and **the last to run wins silently**. ⚠ **A form-only rule is a rule until someone calls the API directly** — and it is asked again when a sync is switched back ON, or the rule has a hole in it |
| 2 | **Address lookup MERGES** — every enabled lookup URL is searched, the candidates de-duplicated and **ranked together** | a city with a qualified-address layer AND an address-points layer just works. ⚠ The ranking is `gis_search.rank_key`, which already existed. ⚠ **ONE layer keeps the CITY's own order**: with nothing to merge, re-sorting would change what every existing tenant already sees |
| 3 | **A disabled API is NOT scheduled and NOT called** | otherwise the switch is decoration — hard-won law 2's mirror, where a control that renders and changes nothing looks identical to a working one. ⚠ And *nobody is looking* is said out loud rather than answered as an empty list, or a clerk files a defect against correct behaviour |
| 4 | ***Working N of M*** and the **State** word count **ONLY ENABLED** APIs | a switched-off API must not drag the count, and a connector is not *Not working* because of one you turned off. ⚠ **The State half needs NOTHING**: since `DEF-INT-5597` that word is `connection.status` and counts no APIs at all — the only way to get rule 4 wrong is to ADD something and break rule 5 |
| 5 | **`DEF-INT-5597` is not undone** | the State column means the **CONNECTOR**, never one of its APIs |

### ⚠ THE KNOWN LIMIT — WRITTEN DOWN, NOT DESIGNED AROUND

**A customer with TWO custom address layers cannot add the second themselves.**
The Kind list is closed and each of our APIs takes one configuration, so the
reachable shape is *the connector's own layer + one of theirs, merged*. The
honest answers for a third are **a manifest line from us** (one file, no screen
code) or **a Runbook**. ⚠ **There is no third, and it must not be invented.**

## BR-INT-079 — A PARTNER'S PROJECTION IS SEPARATE; WHAT IT IS MADE OF IS NOT (CONFIRMED 2026-09-22)

**PO ruling, verbatim** (`CR-132-BRC07`): *"i think we shoudl create seperate enpoint - you can se
the same components that you use, dont write completely new code - what way we can keep it
sepearet"*.

**When a partner's format is a different SHAPE of the same facts, it gets its own address.** When
it is the same shape in another format, it does not — the codec already handles that.

New World's Receipt is the worked case: **header · transaction · GL distributions · payment node**,
with a balancing rule across two levels. Our `/partner/v1/payments` is one flat row. Bending one
into the other would change a contract four other ERP manifests consume, which is the test:
**would serving this partner alter what an existing partner receives?**

⚠ **THE FORMAT IS NOT THE REASON, AND *parameterise it* WAS THE FIRST ANSWER OFFERED.** XML has
been a supported codec since `CR-069` wave D. Reading the specification changed the answer.

**What may NOT be duplicated to serve a new projection:** the door (key, tenant-from-key, access
log, rate window), the module seams, and above all **the GL account resolution** — one place, so a
GL rule changes once. A second resolution presents as a municipality's books being short, found at
a month end by somebody who can see neither code path.

⚠ **AMENDED 2026-10-21 (`DEF-INT-10304`) — THE PARTNER'S TEMPLATE IS THE SHAPE, AND EVERY FILE IS
CHECKED AGAINST IT BEFORE IT LEAVES.** New World's receipt was built as one child element per field
under `<Receipts>`, and its tests compared the output with a fixture recorded from the same code, so
nothing ever compared it with New World's own format. Their confirmed template is **every field an
ATTRIBUTE on its element, under `<ROOT>`**, every attribute always present (`""` when empty),
`VoidedFlag` `0`/`1`, dates MM/DD/YYYY. PO answers of that day: no XSD (*"this was only as
exmaple; not required"*), so the check encodes the confirmed template in code; **a file that fails
is never written to the SFTP folder and never served by the API**; and the API and the SFTP file
switch together (*"Option A — Both switch: one builder, one correct shape"*). **The general rule:
a partner projection is proved against the partner's own template, never only against a recording
of itself.**

## BR-INT-080 — AN UNBALANCED PARTNER RECORD IS SENT, FLAGGED AND COUNTED (CONFIRMED 2026-09-22)

**PO ruling, verbatim:** *"please send receipt even if it is not balance"*, reversing this lane's
own instruction to refuse.

**A refused record is money that silently never reaches the partner's books** — invisible on both
sides, because nobody looks for a record they do not know was withheld. **An unbalanced one is
money that arrives wrong and can be found and fixed.**

Four clauses, and the last three are what make the first safe:

1. **SEND IT.** No refusal and no exception blocks emission.
2. **NEVER SILENTLY.** The record is flagged, the difference is stated **as a figure**, and the run
   reports how many were wrong and by how much, where a manager reads it.
3. **NEVER PLUG IT.** No balancing line, no invented value, no real value adjusted to fit.
4. **LET THEM REJECT IT.** Their importer enforces their rule. A rejection we can see beats a
   record we never sent; pre-empting their control with ours is what hid the money.

⚠ **IT GENERALISES PAST RECEIPTS, WHICH IS WHY IT IS A RULE AND NOT A NOTE.** It is the same
principle as a refused import row going to the exception list rather than being silently forgiven,
and as a seam that cannot answer REPORTING rather than answering zero (`DEF-075`).

## BR-INT-082 — WE NEVER SEND CARD DATA, AND THE CAPABILITY IS NOT BUILT (CONFIRMED 2026-09-22)

A partner format that carries a card number, card type, expiry or CVV is served **without them**. A
card payment is the partner's *charge* tender and nothing else.

⚠ **NOT BUILT AND SWITCHED OFF — NOT BUILT.** No setting, no flag, no mapping entry, no
commented-out branch. Populating one pulls cardholder data into a file and destroys the PCI scoping
that keeps card data out of this product entirely, and **a capability that exists behind a switch
is a capability somebody turns on.** `G130` enforces it for New World.

⚠ **AMENDED 2026-10-21 — FOR THE NAMES ONLY (`DEF-INT-10304`).** New World's confirmed template
lists the four card attributes on every payment node. PO, verbatim: *"Option A — Always write all
four as `""`"*. So for New World the four NAMES now travel, **present and always empty**; card
DATA is exactly as not-built as above — no field, setting or branch can give one a value. `G130`
changed from *"the names never appear"* to *"they never carry a value"*, and
`newworld.validate` refuses a file in which one is not empty before it is sent or served
(decision log 2026-10-21, *"New World / Logos receipt XML: attributes on a `<ROOT>` document;
five answers"*, answer 2).

## BR-INT-083 — A PARTNER MAY POST US A PAYMENT, THROUGH ONE ADDRESS, ON A SCOPE THEY HAVE TO BE GRANTED (CONFIRMED 2026-09-24)

⚠⚠ **THIS REVERSES `BR-INT-071`'S CENTRAL CLAUSE AND THE SUPERSESSION IS STATED RATHER
THAN ASSUMED.** That rule is CONFIRMED and reads, in as many words, *"A PARTNER DOES NOT
POST A PAYMENT TO US"* and *"`POST /api/partner/v1/make-payment/` IS NOT BUILT"* (PO
ruling 2026-09-17). The chain, in order:

1. **PO 2026-09-17** — *"Can a partner post a payment at all? - I want to use batch run to
   take payment feed from Them - not online updates"*. Read as: no partner payment POST;
   we collect on a schedule. **Nothing was built.**
2. **PO 2026-09-18, verbatim and entire: *"they post to us daily"*.** The direction
   reverses. The 2026-09-17 ruling stands for the half it also covered — Invoice Cloud is
   both directions, and the outbound half is untouched — and its refusal of a partner POST
   is gone.
3. **PO 2026-09-24** — the whole design was put to them in a table before a line was
   written (*"tell me how to handle this - dont start the work tell me what you will do"*,
   then *"please confirm in table before you start this APIs"*), confirmed, and then:
   ***"please do"***. The decision log entry of that date is the specification.

### The rule

**`POST /api/partner/v1/make-payment/` is the ONE address on the partner surface that
writes, and a key may call it only if its own scope names `record_payment`.**

* **ONE DOOR.** Checks 1–8 are `partner_api._admit`, unchanged and shared with the eight
  reads. There is no second authorisation path, and the address that creates money is the
  worst possible place for a second answer to *may this caller act*.
* **THE SCOPE IS THE PERMISSION.** `record_payment` is declared by
  `pay_invoicecloud_partner` and by no other manifest, so no ERP key can reach the
  address, and **no key issued before that operation existed holds it** — a key's scope is
  drawn from the operations that existed when it was minted. A key without it is refused
  through check 5, in the **same bytes, the same `404` and the same padded time** an
  unknown key gets (`BR-INT-044`), so a read-only key cannot create money and cannot learn
  that a write door exists.
* **IT DRAWS ITS OWN ROW.** A clerk grants it by ticking *Take a payment* beside five that
  say *Read*. Folded onto a read's tick, granting *read accounts* would silently grant
  *take a payment* — which is `DEF-INT-5622`'s reasoning applied to a permission that
  moves money.
* **THE INTEGRATION WRITES NOTHING ITSELF.** The payment row, its allocations, its journal
  entry and its audit rows are all written by `payments.services.record_payment` inside ONE
  transaction (B2 §2, hard rules 4, 5 and 7). `seams/payments.record_partner_payment` is
  the address, not the writer.
* **HARD RULE 6 IN TWO LAYERS.** The key is `webhook|invoice_cloud:<payment_reference>`,
  checked before any work and backed by `uq_payments_webhook_key`. **A replay is a `200`
  carrying the original payment and `duplicate: true` — never an exception and never a
  `409`**, because a partner told its request failed sends the money again.
* **`tenant_id` AND `company_id` ARE ACCEPTED, IGNORED AND RECORDED**, never refused on a
  mismatch (PO 2026-09-17: *"we cannot tell tenant ID outside our system"*). What they
  named goes on the run row's window text.
* **`late_fee_waived` IS READ AND NOT HONOURED** (`BR-PAY-1150`). The payment is taken —
  the money is real at their end — and the claim is recorded on the run row, so the
  discrepancy is ours to see before it is theirs to report.

⚠ **`fetch_payment` IS STILL NOT DECLARED AND `OQ-INT-12396` IS STILL OPEN.** That
question is about a SCHEDULED PULL, where the second run of a nightly job has nothing to
key on and would record every payment twice. **A push has a key** — their own
`payment_reference`, sent on every call. The two are different mechanisms and this rule
does not touch the pull half.

* **SAVED `posted`, APPLIED AT POSTING, AND THE REPLY SAYS SO — AMENDED 2026-10-21
  (`CR-186-BRC10`).** PO, verbatim: *"we cannot mark payment clear yet"* and *"we have to
  return posted and internal status also should be posted or processing"*; then for every
  method, *"first they will pot the payment - so we crete the record and add posting date;
  then later money is recieved in the bank account ; uitlity will reconcile it bank
  statement that time it is cleared with clearing date"* (decision log 2026-10-21, four
  rulings and the lifecycle entry). So the payment is recorded **`posted`**, applied to the
  bill it names by specific-bill application (excess carried as credit — confirmed
  unchanged the same day), journalled at posting, and stamped with the day's **Invoice
  Cloud deposit batch** (one per provider per day). It becomes **`cleared`** only when that
  batch is reconciled with the bank statement. **The door passes no clearing date, ever.**
  The reply carries `status: "posted"`, `deposit_batch_id` and `deposit_batch_code`, and
  its `unavailable[]` holds only `late_fee_waiver_is_not_honoured` —
  `recorded_as_processing_not_cleared` is REMOVED. The partner's own instruction (*"save as
  cleared … show cleared as posted"*) is superseded: we store and answer one word. The
  next `consumer-info` call shows the reduced balance ($150.00 bill, $120.00 posted →
  `30.0000`).

⚠ **TWO THINGS ARE OPEN AND NEITHER BLOCKS THE ENDPOINT** (it read *"THREE"* until
2026-10-21). `OQ-PAY-12627` is **ANSWERED — `posted`** (above). `OQ-PAY-12626` (which of
their columns is the immutable id — their integration maps whichever they confirm into
`payment_reference`) · `OQ-PAY-12625` (does their settlement file name every payment — the
settlement half only). **`OQ-PAY-12626` blocks GOING LIVE**, which is a different thing and
is stated in its row.

## BR-INT-085 — A TWILIO CALLBACK IS SIGNED, CHECKED AGAINST THE ADDRESS WE PUBLISHED, AND SAVED ONCE PER (MESSAGE, STATUS) (CONFIRMED 2026-10-29)

`X-Twilio-Signature` = base64 HMAC-SHA1 (Auth Token, URL + fields sorted by name), with URL =
`PUBLIC_API_BASE_URL` + the request's path — never the `Host` header. Wrong token, a changed field, a
different URL, no header, no token or no public address ⇒ `401` and NOTHING saved; constant-time compare.
Statuses dedupe on `MessageSid|MessageStatus` (`provider_status_events`, RLS FORCED): `sent` then
`delivered` both land, a retry lands once. `delivered` → the row is delivered; `undelivered`/`failed` →
failed with Twilio's ErrorCode; queued/sending/sent move nothing. Status callbacks carry the utility in the
path; the reply webhook `/api/hooks/twilio/reply` has none.

## BR-INT-086 — A "STOP" REPLY STOPS TEXTS: THE DO-NOT-TEXT LIST AND THE ACCOUNT'S SMS TICK OFF; START AND HELP ARE NOT BUILT (CONFIRMED 2026-10-29)

STOP, STOPALL, UNSUBSCRIBE, CANCEL, END, QUIT (or Twilio's `OptOutType=STOP`) puts the number (E.164) on
the do-not-text list — holding every text already queued to it — and turns OFF the *SMS reminders* tick on
every account this utility texted at that number, through `apps/customers/sms_opt_out.py`, audited
(`account.sms_reminders_turned_off`). Applied for exactly the utilities that send through the sender the
reply was addressed to AND have texted the number. Twilio `21610` on a send is the same fact. **START and
HELP are NOT built** (PO: *"ONly Stop option is required"*); Twilio's Advanced Opt-Out answers them at the
carrier; a START does not re-tick anything here.
