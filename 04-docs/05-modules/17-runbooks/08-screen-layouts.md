# 17 · Runbooks — screen layouts

**Eight screens, twenty-nine drawn states, written while looking at the seventy-five wireframes already in
this repository at `wireframes/`.** Each wireframe is a rendered PNG paired with a build sheet of the same
name; the sheet lists that screen's regions in order with the copy verbatim, the component, and the
size/state/rule. The sheets carry their own acceptance line and it is the contract:

> *Acceptance: the built screen shows exactly these N regions in this order with this copy, at these sizes,
> in these states. A region missing, a control added, a word changed or a size off is a defect of kind
> Screen, copy or layout. Sample values are illustrative; the words around them are not.*

**So this file does not restate the copy — the sheet is the copy.** It gives each screen its id, its route,
what it answers, its regions in order, and the wireframe file to compare a built screen against. Where the
pack and B14 disagree, the rule wins; every such place is in `09-component-inventory.md`'s closing section,
and the entries below cross-reference it rather than repeating it.

Read at product `2.128.2` (the pack's own staleness stamp), sheets generated by
`10-scripts/runbooks_wireframes.mjs`.

## Why eight screens covers thirty-four runbooks

**`RBS-004` and `RBS-006` are RENDERERS, not pages.** `RBS-004` renders a runbook's *definition* — its scope,
its parameters, its steps, what it produces. `RBS-006` renders a run's *report* — a composition of the twelve
result blocks (`09-component-inventory.md`). Neither knows anything about a particular runbook: both read a
declaration.

So **adding runbook 23 needs no new screen and no frontend change at all.** It needs one Python module
declaring `key`, `kind`, `category`, `subject_type`, `parameters`, `resolve`, `steps`, `guards`, `ports` and
`report` — `12-the-contract.md` — and it appears on `RBS-002` Templates, sets up on `RBS-004` and reports on
`RBS-006` because those three screens are driven by the registry. That claim is `RB-020`'s *done looks like*
and it is what the eight-screen count rests on.

**The thirty-four.** Runbooks are numbered **1 to 35 with no 7** — the PO ruled *"Keep as numbered: 1 to 22
with no 7"* on 2026-09-05 and the reserved block extends the same series — which is **34 runbooks**: 21
defined and 13 reserved (23–35). ⚠ The definitions page's own summary line reads *"Defined 21 · reserved 14"*;
21 + 13 = 34 and 21 + 14 = 35, so **one of those two numbers is wrong in the source** and it is recorded here
rather than picked. The count that is checkable from the drawings is 34: `RBS-004-R1 … R27` less `R7` = **26
setup renderers drawn**, `RBS-006-R1 … R22` less `R7` = **21 result renderers drawn**, and runbooks 28–35
carry commitment cards (`RB-128`–`RB-135`) with no renderer drawn yet.

**Sheet arithmetic, so a missing file is visible:** 28 state sheets (`RBS-007`'s one sheet covers both its
states) + 26 setup renderers + 21 result renderers = **75 sheets, 75 pictures, 150 files**.

**The batch-progress pattern is not invented here** — it copies what the product already does when it seeds a
new utility, and the three properties are what make a run legible: **every step is listed before the first
one starts** (the PO asked to see all of them up front rather than watch a list grow); **a step that does not
run carries the reason it did not**, including *Never reached*; and **step labels are written for a clerk with
no internal code in them**.

**Step 1 pins the scope once.** *Matches 1,004 accounts* and the button reads **Check these 1,004 →**. An
account that becomes past due during the run is not in the review list and is not acted on (`RB-008`).

**Step 3's *Why* column is load-bearing:** every row states the rule that decided it in plain words — *First
tier due* · *Plan in good standing* · *Medical protection* · *Over the fee limit*. That is what makes the run
auditable by the person approving it rather than by an engineer afterwards (`RB-009`).

**Step 4 is the one irreversible act and it uses the danger tier** (rule 6) — outlined accent, not the
standard primary. **The consequence box sits directly above the commit and never after it** (rule 11). Its
third line is the one to keep: *Leave 412 for next run.* — the cap means 412 accounts are deliberately left,
and the screen says so rather than letting a clerk discover it afterwards.

**Step 6 says *Queued*, not *Sent*.** Until a delivery provider is connected nothing leaves the building and
the copy must not claim otherwise. **Two downloads, matching the import runner's existing pattern** — one
file of what happened, one of what did not, each row carrying its reason and its fix. **Every failure links
to the screen that repairs it; a failure with no route to a fix is a defect in the runbook, not a fact about
the account.**

**On the cap refusal, *Send first 400* is a deliberate choice a clerk makes, never what the system quietly
did.** On a failed check, the steps that never ran read **Never reached** rather than sitting blank — the
exact gap the seeding screen had to fix, and worth copying rather than rediscovering.

⚠ **`RBS-005.5` and `RBS-005.6` drop the `←` from the kicker** (*Collections ladder*, not *← Collections
ladder*) while steps 1–3 keep it. That is rule 1 read correctly, not an inconsistency: a `←` names where the
page EXITS to, and once Applying has begun there is no exit backwards. Keep it.

### Seven places the Check path departs from these sheets, and why — `CR-075` wave C task `C4`, 2026-09-06

⚠ **EVERY `RBS-005` FRAME IS DRAWN ON RUNBOOK 8, THE COLLECTIONS LADDER, WHICH IS AN ACTION.** The Check path
built in wave `C` runs runbook 1, *Can we bill?*, and **a Check sends nothing and CAN send nothing** —
`BR-RBS-002`: the write capability is ABSENT, not withheld. Six sentences and one control therefore cannot be
carried across literally. Each is recorded here rather than changed silently, in the direction this pack
already records: **where a sheet and a rule disagree, the rule wins.**

| 2 | `RBS-005.2` subtitle *"Nothing has been sent."* | **"Nothing has changed."** | Same posture, true of a Check. |

## Divergences settled by CR-075 wave C, tasks C1a and C1c (2026-09-06)

**Stamped here, in the file that describes the screens, because a lane building against a sheet reads the
sheet.** Each is a case where the drawing and a signed rule disagree and the code had to pick one. None was
smoothed over and none is a licence to ignore the sheet elsewhere.

### 1 · Every percentage in the pack is drawn at 0 or 1 decimal · **the rule wins, at 2**

`09-component-inventory.md` Part 4 §7 measured it across all seventy-five sheets: `+38%`, `+4.7%`, `+30.4%`,
`15%`, `2.0%`, `0.05%`, `61%`, `92%` — **not one percentage anywhere is drawn at two decimals.** CLAUDE.md
hard rule 2 says percentages **display 2**, re-signed by the PO on 2026-08-22 in the words *"MOney 4 decimal,
percentage 6 decimal , display both 2 decimal"*.

**The rule wins and the sheets are not followed on this point.** `RBS-006-R16`'s `+4.7%` is built as
**`+4.70%`** and `RBS-006-R4`'s `+38%` as **`+38.00%`**. Both are derived from money and are squarely inside
the rule; a signed money rule is not overturned by a drawing.

⚠ **What is NOT changed by this stamp:** `61%` on a progress bar and `300%` in a parameter label are not
hard-rule-2 percentages — one is a proportion of a bar's width and the other is a threshold inside a LABEL.
Part 4 §7 already draws that line and it stands. A screen drawing one of those keeps the sheet's own figure.

**Built:** `07-frontend/src/components/PercentCell.tsx` — `formatPercent`, `PercentCell`,
`PERCENT_DISPLAY_DECIMALS = 2`. It lands beside `MoneyCell`, in the **shared kit**, not in a runbooks-local
helper (B14 rule 36).

### 2 · A percentage's CONVENTION is a required argument, because the product stores both

Not a divergence from a sheet — a gap the sheets cannot fill, recorded here because the next screen to draw a
percentage will hit it. `06-backend/core/money_fields.py` states that a percent is stored *"either as a
fraction (`0.062500`) or as percent points (`40`) — the product uses both conventions"*. `taxes.rate` holds
`0.062500` and means 6.25%.

**A formatter that picks one is wrong by a factor of 100 on the other, on a money path, silently** — and
magnitude cannot decide it: `0.5` is an ordinary value under both readings (50.00% as a fraction, 0.50% as
points). So `formatPercent` takes the convention as a **required** argument and `tsc` refuses a call that does
not say. The reasoning and the worked figure are in `12-governance/02-decision-log.md`, 2026-09-06.

### 3 · The coverage grid's RESULT screen is not drawn, and the grid mode is built from one sentence

`RBS-004-R24` draws the coverage grid's **setup**. There is no `RBS-006-R24` among the forty-eight result
sheets — the same absence wave `F1` records for runbook 23, where it says in as many words that *"there is no
build sheet to compare against and law 6 cannot be performed."*

The `Records` block's **grid display mode** is nevertheless phase-1 work, because phase 2's coverage grid IS
that mode (`10-execution-plan.md`, task C1a). It is built from the one sentence the pack does give —
`RBS-004-R24`'s own Outcome box, quoted verbatim in the component and in its test:

> *"A grid: 21 clean · 2 estimated · 2 refused, each cell opening that account's test bill with the engine's
> own refusal sentence."*

**Every element traces to that sentence and nothing else was invented.** The three states are its three
words; the counts 21 / 2 / 2 are its counts and are asserted as such; *each cell opening* is why `to` is
**required** on every cell and why the component cannot express a dead one (`DEF-CWP-3925`: the portal
shipped a front page with two working doors out of eight, and G13 cannot see that shape — it asks whether a
prop is passed, never whether a refusal is still true).

**When wave `F1` draws the frames for runbook 23, `07-frontend/src/components/RecordGrid.dom.test.tsx` is the
file that has to change**, and the component is corrected against the frame then. Recorded so that lane finds
a stated choice rather than rediscovering a gap.

### 4 · What these eight components do NOT settle

* **The Outcome box's word budget.** `09-component-inventory.md` Part 4 §1 measured 28 boxes at **14–88

## Divergences settled by CR-075 wave C, task C2 — the result renderer (2026-09-06)

### 5 · The records table's EMPTY state draws NO call to action · **the sheet and rule 17 both yield**

B14 rule 17 asks an empty list for *what is missing and the action that fills it*, and `EmptyList` — the
component every other list in this product uses — makes `ctaLabel` **required** for exactly that reason.

**That is right for a list nobody has filled yet, and wrong for a Check that found nothing.** *"Nothing stops
billing."* is a GOOD OUTCOME rather than a gap; there is no action, and offering one would mean inventing a
button that opens onto nothing (`BR-SHL-025`'s shape, and hard-won law 2's mirror). A disabled button reading
*Nothing to fix* over a clean result is worse still: it reads as a failure.

**So `RecordsPayload.empty` carries two fields and no CTA, and `RecordsBlock` renders that state itself
rather than letting `DataTable` reach `EmptyList`.** The type already carried the decision before the code
did — it was declared that way by `C1b` — and this is the record of why.

⚠ **`DataTable`'s `empty` prop is still passed, with real words, and is UNREACHABLE BY CONSTRUCTION.**
`DataTable` draws `EmptyList` only when `totalRows === 0 && !loading && no query state`, and the block
returns before that. The words are real anyway (`runbooks.records.empty.cta` / `.reason`, eleven catalogues)
because an unreachable branch furnished with a placeholder is a placeholder that ships the day the branch
becomes reachable.

### 6 · `RBS-006-R1`'s KPI strip draws FOUR tiles and the report composes THREE · **both are correct**

The fourth is *12s · Took*, and **a duration is not a fact about the RESULT**. The report is composed at
close and FROZEN (`BR-RBS-020`); the elapsed time lives on the run row (`runbook_runs.started_at` /
`finished_at`), which is a different lifetime and a different owner. Putting it in the report would freeze a
number that the run record already holds and can restate.

**So `configuration_check.report()` emits three tiles and the SCREEN composes the fourth from the run it is
already holding.** `RunResultView.header.took` is that field, and it is absent while a run is still going —
which the strip must show as an absence rather than as `0s`.

### 7 · `RBS-006-R1` draws six REGIONS while runbook 1's report carries six BLOCKS, and they are not the same six

The frame's regions are page head · KPI strip · chain · toolbar · table · pagination footer. The report's
blocks are verdict · kpis · chain · breakdown · records · downloads. Reading one beside the other settles the
composition rule, which is the one thing `RunResult.tsx` decides:

| The frame draws | It comes from |

| the head's **sub-line**, *"3 things stop billing."* | the **leading `verdict` block's `count`**, word for word — so a leading verdict becomes the sub-line and is **not drawn again below it** (B14 rule 32: one sentence per section, and printing it twice is what the description budget exists to stop) |
| the head's **`↓ Findings`** action | the **`downloads` block**, lifted into the header rather than drawing a row of its own |
| regions 2–6 | every other block, **in the report's own order** |

⚠ **`breakdown` IS ABSENT FROM R1'S FRAME AND IS DRAWN ANYWAY, WHICH IS THE IMPORTANT HALF.** A sheet is a
region list rather than a whole screen — this file's own *How to read a sheet* section says so, and 39 of the

## Divergences settled by CR-075 wave D, task D2 — `RBS-001`, the Runbooks home (2026-09-06)

### 1 · The sheet draws ONE pagination footer · **the built screen draws TWO**

### 2 · `.2` and `.3` draw ONE page-head action · **the built screen carries all three in every state**

### 4 · `.1` draws a kept **Draft** row · **there is no draft, and none is drawn**

`DEF-RBS-4289`, filed by wave C and still open: `RUN_STATUSES` holds queued, running, awaiting_approval,

## Divergences settled by CR-075 wave E, task E4 — what the wire cannot carry (2026-09-06)

**Stamped here for the same reason as the section above: a lane building against a sheet reads the sheet.**
Wave `C` built `RBS-004` over a hand-made view model, so a sheet could be honoured with a value the product
does not have. Wave `E` connected the same screen to the real endpoint (`DEF-RBS-4308` — until it did, the
screen threw in a browser) and **five values the sheets draw turned out to have no field behind them at all.**

**The rule applied to all five is one sentence: an absent value draws NOTHING — no line, no dash, no
placeholder — and the gap is filed rather than filled.** A placeholder here is the screen inventing a fact,
and every one of these is a fact about a customer's runbook.

### 1 · The one-line PURPOSE under the title · **not drawn** (`DEF-RBS-4309`)

`RBS-004.1` draws *Finds what stops a bill run before it starts* as the subtitle, and `RBS-002.1` draws it on
six cards. `contract.py`'s `RunbookDefinition` has **no field for it** — key, name, kind, category,
subject_type, unit_of_work, steps, triggers, tags, parameters, guards, requires, ports, and nothing else. So
`RunbookSetupView.purpose` is OPTIONAL and the page head draws its category chip alone. The durable fix is a
one-sentence `purpose` on the definition, written once by the runbook's author.

### 2 · Every step's WHY line · **not drawn** (`DEF-RBS-4285`, already stamped by `C3`)

Unchanged by this wave and repeated here only because it is the same shape and the same rule.

### 3 · The SCHEDULE in words · **the TRIGGER is drawn instead** (`DEF-RBS-4342`)

`RBS-004.1` draws *Runs · Mondays 07:00* and `RBS-004.7` draws *Schedule set to Mondays*. The wire carries
`trigger_kind` plus a five-field `cron`, and **printing `0 7 * * 1` at a clerk is B14 rule 32's own ban** —
no internal code in clerk-facing copy. The row therefore reads **Manually · On a schedule · On an event**,
and the Activity phrase is **Schedule changed**. No shipped runbook carries a cron today (`trigger_kind`
defaults to `manual` and `cron` is null on every row), so nothing is lost meanwhile. The durable fix is a
human schedule phrase beside the cron, or a cron-to-words formatter in the shared kit with its own tests.

### 4 · The Scope tab's values are DECLARED DEFAULTS, not what this tenant set (`DEF-RBS-4338`)

`RBS-004.3` draws *Accounts included · Past due over $5.00* and `BR-RBS-042` says a tenant SETS input values.
**Nothing stores one.** `services.EDITABLE_SETTINGS` is eight schedule-and-limit fields — `enabled`,
`trigger_kind`, `cron`, `event_kind`, `timezone`, `cap`, `gate_mode`, `visible_to_roles` — and the definition
document holds parameter DEFAULTS. Today the two are the same string for every tenant, so the tab is
accidentally right; the first admin to change a scope value would find nothing to change it with.
**`Change scope` therefore still refuses**, and `setupVersioning.dom.test.tsx` fails the day a parameter
field joins `RunbookEditBody` — which is the hold-expiry test hard-won law 2 asks for.

### 5 · An enum parameter's VALUE arrives as a code · **it is de-cased** (`DEF-RBS-4339`)

`Parameter.choices` is a tuple of bare strings, so the wire says `blockers_and_warnings` where the sheet says
*Blockers and warnings*. Three answers were possible and two are worse: printing the code breaches rule 32,
and drawing *Not set* over a parameter that HAS a value is simply false. **It is de-cased**, and the reason
that is defensible is consistency rather than convenience: `Parameter.label`, `Step.label` and `Guard.label`
are ALREADY English strings written in Python and passed through untouched by design, so a de-cased value is
the same class of string as the label beside it. A per-runbook lookup table in the front end was refused
outright — it would break `RB-020` (*adding runbook 23 needs one Python module and no frontend code*). The
durable fix is `choices` becoming `{value, label}` pairs.

### 6 · What was NOT a divergence

The Activity tab is drawn exactly as `RBS-004.7` lists it — version, summary, actor, moment, newest first —
and **`v4` stays on screen** under B14 rule 31's own escape clause, which this file already grants. The
row's real id is the version NUMBER on the wire, so there is no uuid on that path to leak by accident.
