**No `verdict` band and no `chain`**, and both are deliberate. A verdict band would print the same
outcome the KPI strip already carries, which is the description budget rule 32 exists to protect; the
chain earns its place on runbook 1, where *which of ten steps stopped* IS the finding, and here all
three steps run on every cell.

**No chips.** `RecordsPayload` allows them and `RBS-006-R1` draws them for runbook 1. On this screen
they would be dead UI: `RunResultPage` holds the chip in state and **nothing filters the frozen
report's rows by it**, so pressing *Refused 2* would move a highlight and no cells (hard-won law 2).

**No `downloads` button**, for runbook 23's own reason: the two result files stream
`runbook_run_records` and nothing writes a record row yet, so the button would download an empty file.
**When a wave persists record rows, this screen gains a `downloads` block and this paragraph is what to
delete.**

## Where this sheet DIVERGES from `RB-124`, each with its reason

* **The period is the last whole calendar month, where the card's scope row reads *Period: The next
  cycle*.** A period that has not happened has no reads, so a grid over it would be 25 refusals and
  would prove nothing about a utility's data — the exact opposite of what the go-live artefact is for.
  It is runbook 23's own default (its judgment J8) and it is a parameter a clerk can change.
* **A master account is not a cell, and it is COUNTED in region 5 rather than dropped.** `BR-CUS-1010`
  makes a Master Account the owner's account at an ADDRESS: it names a premises and no unit, so it has
  no plan, no service mix and no cycle to sit in.
* **The card's *estimated or defaulted* is built as *estimated* only.** Nothing in `billing.contracts`
  records that a quantity was DEFAULTED rather than read or estimated, so a cell claiming to detect one
  would report a fact this product does not hold.
