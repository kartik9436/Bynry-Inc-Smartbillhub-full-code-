## 0 · The rules every field-app endpoint follows

These are the contract between a handset that may be days out of date and a server that ships the same day. Each is
from the design; the server's current state is stated beside it.

| # | Rule | Source | Server today |
|---|---|---|---|
| 1 | **Older app versions keep working.** A technician on a route has the old build until they reach wi-fi, *"and perhaps until the app store approves the next one — days"*. So a change to a field-app route is **ADDITIVE ONLY**: a field is added, never renamed or removed; a kind is added, never repurposed. An older handset keeps sending what it sent; an unknown field the server adds is preserved by the handset and sent back untouched | Data §9, `R116`, `R117` | The sync already stores an unknown item kind *"as received and flagged, never dropped"* (`RECEIPT_KINDS` = `ITEM_KINDS` + `unrecognised`, TECHNICIAN SYNC DESIGN (2)). No version is read from a request |
| 2 | **A version too old to be served is refused BY NAME, never served wrongly.** The payload carries a schema version and the handset refuses a version it does not know rather than storing nulls; the server's mirror of that is a minimum supported app version, answered as a refusal the app can show (*"update the app"*) — never a 500 and never a silently partial answer. **The minimum is raised only when an additive change is impossible**, and captured work from the older build is still accepted for sync (capture never depends on the network, `R113`) | `R117`, Security §6 *"No blocking on a weak signal"* | **BUILT 2026-10-21** (`DEF-FLD-10355`; read *"NEW — no field-app route reads an app or schema version"* until then): `core/field_app_version.py`, `FIELD_APP_MIN_VERSION`, 426 `app_too_old`; captured-work routes exempt |
| 3 | **The tenant comes from the credential, never from the payload.** A tenant id in a request body is an attack surface; a tenant-bound credential means a handset cannot send to the wrong one | `R127`, Data §12 | Routes are path-tenanted (`/api/{tenant}/…`, PO 2026-08-10) and checked against the session; the capture token is signed with its tenant (`"t"`). No field route reads a tenant from a body. ✓ |
| 4 | **Data items are answered SYNCHRONOUSLY, one receipt per item** — accepted · duplicate · refused, never a boolean for the batch. The technician acts on a refusal (RW-27, FF-50) | `R126`, `R48` | `POST /work/mobile/jobs/{id}/sync` ✓ (per ORDER only — §2 #N1) |
| 5 | **Photographs are BINARY, one per request, hash declared first; never base64, never inside JSON.** 10 MB request ceiling | `R124`, Data §12 | `PUT /work/mobile/photos/{photo_id}` takes the raw body or a multipart `file` and checks the declared `sha256` ✓ |
| 6 | **A 200 on a photograph means the bytes are durably stored, never that a job was enqueued** — the handset deletes its copy on that answer | `R125` | `photo_links.receive_bytes` commits the bytes to `staged` before enqueueing and answering ✓ |
| 7 | **Every mutating route is idempotent on a key minted AT CAPTURE**, and a repeat answers *duplicate* and changes nothing | `R45`, `BR-WRK-042` | Sync receipts (`work_sync_receipts.key`), photo links (unique `(tenant, photo_id)`), attachments (`(tenant, work_order, key)`) ✓ |
| 8 | **Proved on PostgreSQL**, not the suite's SQLite. A refused row must not poison the batch, and SQLite has no aborted-transaction state, so the broken version passes everything (hard-won law 14) | T-46 | `tests/test_us_wrk_044_sync_pg.py` ✓ for the order sync; every NEW batch route needs its own `_pg` test |
| 9 | **Paged, no hard cap** — any list a handset reads at volume (readings, nearby work, asset search, the change feed) is server-paged with `core.pagination`'s clamp, and no route enforces a maximum count per tenant | `NFR-3`, `NFR-5`, T-40 | `/changes` and `/jobs/{id}/readings` page ✓ |
| 10 | **A technician sees only their own** — no route takes a technician id; scope comes from `mobile.technician_of(actor)`, and another technician's job is a 404 byte-identical to one that does not exist | `US-WRK-041` TC-6, HR-1 | ✓ (`FieldAppRole` + `require_own_job`) |
| 11 | **Money is read, never written.** No route in this file writes a money row | `R16` | ✓ — and none may be added |

## 8 · Volume the routes must carry (Data §12)

Normal day at the top of the ICP: ~12 of 20 staff in the field, **2,400 items** (4,800 with three read routes), ~460
photographs. Everybody syncs at the depot between 16:00 and 17:00: **~96 batch requests and ~8 photograph uploads a
minute.** Limits: 50 items per batch (~1 MB) · one photograph per request, 10 MB ceiling · 2 batches and 1
photograph in flight per device · **~600 requests a minute per tenant** — twelve technicians syncing at once, with
headroom. ⚠ The photograph sizes behind these figures are 300 KB; the signed rule is 100 KB (`03-field-map.md` §12).
