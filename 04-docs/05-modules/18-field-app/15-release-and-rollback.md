# 18 · Field app — release, rollback and the beta (T-57 to T-60)

**Change:** `CR-187-BRC10` · **Tasks:** T-57 build pipeline, T-58 version on screen, T-59 the beta, T-60 rollback ·
**Written:** 2026-10-21, lane RELEASE. Store listings and privacy declarations are `14-store-listing.md` (T-56).

**The one-paragraph version.** The field app is two things that ship differently: a **native binary** that goes
through Apple's and Google's review (days), and the **JavaScript** inside it, which can be replaced over the air in
minutes. Every build carries the product version (`2.590.0`, the same number as the web app and the server) and its
own store build number, and the app shows both — *2.590.0 · build 7* — in the menu, on Settings, on the splash and on
sign-in, so a technician reporting a fault names exactly what they are running. A bad JavaScript update is undone by
re-publishing the last good one; a bad binary cannot be recalled from handsets that have it, so its rollout is halted
and a fixed binary is shipped on top. The server keeps older builds working by changing field-app routes additively
only — and a build too old to serve is refused by name with a minimum-version refusal (§5.3; built 2026-10-21,
`DEF-FLD-10355`, which read *"not built yet … a blocker for the first store release"* until then).

## 1 · How it is built (T-57)

| Piece | Where | What it does |
|---|---|---|
| Build profiles | `field-app/eas.json` | **development** (a dev client for engineers, internal install) · **preview** (internal install, Android as an APK, for the office and the beta crew before store review) · **production** (store builds: App Store / an Android App Bundle) |
| Update channels | `eas.json` → each profile's `channel` | `development`, `preview`, `production`. A build only ever listens to its own channel, so a preview update can never reach a production handset (`tests/release/config.test.ts`) |
| Runtime version | `app.json` → `runtimeVersion.policy: "fingerprint"` | Expo hashes the native layer (native packages, their config, `app.json`'s native fields). Adding a native package changes the hash and therefore needs a new store build — by construction, not by memory |
| Update behaviour | `app.json` → `updates` | checked when the app starts (`ON_LOAD`), never waited for (`fallbackToCacheTimeout: 0`), applied on the **next** cold start. A technician is never made to wait at the splash for a download, and the running JavaScript is never swapped mid-shift |
| Build number | `app.json` → `ios.buildNumber` / `android.versionCode` (both `1` now), `eas.json` → `cli.appVersionSource: "local"` | the committed number is the truth; a production build is a commit that moves it. Both stores refuse a number they have seen, so a reuse cannot ship |

| Pipeline | `.github/workflows/field-app-eas.yml.disabled` | type-check, tests and `G35`, then `eas build` or a signed `eas update`, started by hand. **Disabled**, like every workflow in that folder, by the PO's ruling of 2026-09-04 (*"I dont want any github actions to run on this project"*). ### 1.1 · Signing — keys in CI secrets and in EAS, never on a laptop (Security §4)

| Key | Held by | Used for |
|---|---|---|
| iOS distribution certificate + provisioning profile (with **Critical Alerts** and push capabilities) | EAS credentials service (generated by EAS with access to the Apple team) | signing every iOS build |
| App Store Connect API key (Issuer ID, Key ID, `.p8`) | EAS credentials | `eas submit` uploading to TestFlight |
| Android **upload** keystore | EAS credentials (generated by EAS) | signing the App Bundle for upload |
| Android **app-signing** key | **Google Play App Signing** — Google holds it | signing what users install; a lost upload key can be reset by Google, a lost app-signing key could not |
| Google Play service-account JSON (release permission) | EAS credentials | `eas submit` to the internal track |
| Over-the-air **update signing** private key | GitHub secret `EXPO_UPDATES_CODE_SIGNING_PRIVATE_KEY` | signing every update; the binary carries the matching **certificate** and refuses an unsigned or wrongly signed update |
| EAS robot token | GitHub secret `EXPO_TOKEN` | the pipeline talking to EAS |
| Firebase configs | GitHub secrets `GOOGLE_SERVICE_INFO_PLIST`, `GOOGLE_SERVICES_JSON` (base64) | Crashlytics; written into the build, never committed |
| PostHog | GitHub secrets `EXPO_PUBLIC_POSTHOG_KEY`, `EXPO_PUBLIC_POSTHOG_HOST` | usage events and flags. A PostHog project key is designed to be public in an app; it is a secret here only so it is set in one place |

**Update signing, once, on a secure machine (not in this repository's container):**
`npx expo-updates codesigning:generate --key-output-directory keys --certificate-output-directory certs --certificate-validity-duration-years 10 --certificate-common-name "SMART360 Next Field"`,
then `npx expo-updates codesigning:configure --certificate-input-directory certs --key-input-directory keys`, which
adds `updates.codeSigningCertificate` and `codeSigningMetadata` to `app.json`. **Commit `certs/certificate.pem`;
put `keys/private-key.pem` into the GitHub secret and a password manager; delete the local copy.** Until this is
done the pipeline's update step refuses to run (it requires the secret), which is the safe direction.

### 1.2 · The first preview APK — buildable without Firebase and without a map key (2026-10-22)

The `preview` profile (internal distribution, Android APK, channel `preview`) builds with **neither** the PO's

Build command, from `field-app/` on a clean commit (`cli.requireCommit`), with `EXPO_TOKEN` set:
`npx eas-cli@latest build --platform android --profile preview --non-interactive`. EAS generates and holds the

## 2 · How a release goes out

1. **Version.** `python3 10-scripts/allocate.py version --bump change` names every file to move; the field app moves
   with the product. The store build number moves in the same commit when a binary will be built.
2. **Changelog** entry for the version, in the same commit (`G35` clause 4).
3. **Build** the production profile for both platforms. **Submit**: iOS to TestFlight, Android to the **internal**
   track as a **draft** (`eas.json` → `submit`). Nothing becomes public without a person pressing release.
4. **Beta / internal check** on that exact binary (§6) — the same binary is promoted, never rebuilt.
5. **Release in stages.** Apple: *phased release for automatic updates* (7 days: 1 % → 2 → 5 → 10 → 20 → 50 → 100 %).
   Google: *staged rollout* starting at 10 %. These are what make §5.2 possible.
6. **JavaScript-only fixes** after that go by `eas update` to the `production` channel, with a message naming the
   version (`2.591.0`). The pipeline refuses an update with no message.

## 3 · The version on screen (T-58)

The product version and the **running binary's** build number, as the boards draw them (FF-01, FF-09):
**`2.590.0 · build 7`**. Shown in the menu foot, on FF-51 Settings → About, on FF-01 Splash and on FF-05 Sign in
(`field-app/src/release/build.ts`, key `field.nav.versionBuild`).

The build number is read from the binary (`CFBundleVersion` / `versionCode`) and **not** from `app.json`, because
`app.json` is bundled with the JavaScript: after an over-the-air update it would name the build the update was made
from, not the build on the handset. So after an update the screen reads, truthfully, *2.591.0 · build 7* — new
JavaScript on the old binary — which is exactly the pair a defect report needs. Where a binary has no build number
(Expo Go, a test) the version is shown alone. `tests/release/build.test.tsx` mounts the menu with a binary reporting
build 412 and an `app.json` reporting 1, and fails if the label is taken from the wrong one (proved red by putting
the bare version back).

## 4 · Telling the reporter which build to look in (the maintenance process, step 8)

A technician who reports three things and hears nothing back stops reporting. So:

1. **Reporting.** The report names the line from the menu foot — *"2.590.0 · build 7"* — plus what they were doing,
   the screen (its name on the top bar), and roughly when. A photo of the screen is fine (screenshots are blocked
   only on screens showing a customer's name, account or balance, Security §3).
2. **Filing.** The office files it as a defect with that line in it (`10-scripts/file_defect.py … --id-module FLD`),
   so every field-app defect carries the build it was seen on.
3. **The fix ships** either as an update (JavaScript) or as a new binary (native).
4. **The reply names what to look for**, in one of exactly two forms:
   * *JavaScript fix:* **"Fixed in 2.591.0. Open the app with signal, close it fully, open it again — the menu will
     read 2.591.0 · build 7."** (The update downloads on one start and applies on the next.)
   * *Native fix:* **"Fixed in 2.592.0 · build 8. Update the app from the App Store / Play Store; the menu will read
     2.592.0 · build 8."**
5. If the reporter's menu still shows the old line a day later, that is itself a finding (a handset not receiving
   updates) and is filed.

## 5 · Version and rollback — stated before shipping (T-60)

*In the style of a change request's §5. The maintenance process's rule is "Code only — Revert the commit. Done." —
and for a native app that rule is not enough on its own, because a binary already installed on a handset cannot be
reverted. The honest statement of what can and cannot be undone follows.*

**Version:** the first store release carries the product version current at the time it is cut (this lane leaves
`2.590.0` unmoved; the release cut moves it with `allocate.py version`) and **build 1** on both stores.

### 5.1 · A bad JavaScript update — undone over the air, in minutes

* **Undo:** re-publish the last good update to the channel —
  `eas update:republish --group <last good update group id>` (the id is on expo.dev → Updates, or
  `eas update:list --branch production`) — or, if no update was good, send every handset back to the JavaScript
  embedded in its binary: `eas update:roll-back-to-embedded --channel production`.
* **Who gets it, and when:** every handset on that runtime fingerprint, **the next time the app starts with a
  signal, applied on the start after that.** A handset that stays offline keeps the bad JavaScript until it next
  starts with signal — stated, not hidden; for a whole-shift offline crew that can be the rest of the day.
* **Re-applying the bad update** is impossible by accident: republish creates a new update, newer than the bad one.
* ⚠ **NOT REVERSIBLE THIS WAY — an update that added a handset database migration.** The handset store is
  migrated forward only, and an older JavaScript bundle **refuses to open a store written by a newer one**
  (`db/database.ts` → `migrate()`: *"this store was written by a newer build"*). Rolling such an update back would
  leave the technician unable to open their day **with their unsent work inside the refused store.** So an update
  that carries a migration is **rolled forward** (a fix published on top), never back, and is marked as such in its
  update message and its changelog entry before it ships. Better: ship handset migrations in a store build, where
  the runtime fingerprint already separates old and new.
* **Data already sent by the bad update stays sent.** Readings, photos and close-outs it captured and synced are on
  the server; correcting them is a correction on the server (new rows, hard rule 4), not a rollback.

### 5.2 · A bad native build — halted in both stores, never recalled

* **Apple.** App Store Connect → the version → **Pause Phased Release** (stops automatic updates to more users; can
  stay paused up to 30 days in total). If it must stop completely, **Remove from Sale**. Neither touches handsets
  that already installed it. TestFlight: **Expire Build**. Then ship a **new binary with a higher build number**
  carrying the last good code, and request an **expedited review**. There is no way to give a handset back an older
  binary.
* **Google.** Play Console → the release → **Halt rollout** (stops new installs and updates of it). Then roll out a
  **new release with a higher `versionCode`** carrying the last good code. Play cannot install a lower `versionCode`
  over a higher one.
* **For the handsets that already have it:** if the fault is in JavaScript, §5.1 reaches them in minutes. If it is in
  native code, the server's minimum-version refusal (§5.3) is what stops the build from doing harm, and the
  technician sees *"update the app"* instead of a wrong answer. Captured work on those handsets is never thrown away
  to fix it (Security §1, *"Never: a silent sign-out that discards work"*).
* **The web field app is the fallback for the crew** while a binary is halted — it stays live until T-72 decides
  its future (decision log 2026-10-21, conflict #9).

### 5.3 · What the server keeps compatible

* **Additive only.** A field-app route gains a field, never renames or removes one; a sync item kind is added, never
  repurposed (`07-endpoints.md` §0 rule 1, `R116`). An older build keeps sending what it sent; the server stores an
  unknown kind as received and flagged, never dropped.
* **A minimum supported app version, refused by name.** Where an additive change is impossible, the server answers
  a too-old build with a refusal the app shows as *update the app* — never a 500 and never a partial answer — and
  **still accepts that build's captured work for sync** (`07-endpoints.md` §0 rule 2, `R117`).
* **How it is built** (`07-endpoints.md` row **N7**, `DEF-FLD-10355`, 2026-10-21 — this bullet read *"THAT REFUSAL
  IS NOT BUILT"* until then). The app sends `X-Field-App-Version` (the product version), `X-Field-App-Build` and
  `X-Field-App-Platform` on every request (`field-app/src/release/appUpdate.ts`, both HTTP clients). The server
  (`06-backend/core/field_app_version.py`) compares the version with **`FIELD_APP_MIN_VERSION`** — an environment
  setting, platform-wide, default `0.0.0`, which refuses nothing — and answers a lower one **426** with
  `params.reason: "app_too_old"` and `params.minimum`. **To stop a bad binary: set `FIELD_APP_MIN_VERSION` to the
  fixed version in the deployed environment and restart the web tasks** (a `.env.example` edit reaches no running
  host). A request with no version header (the web field app, curl) is never refused. The routes that carry
  captured work up (the two sync batches, a route's readings, photographs, a route's turn-in) and token refresh and
  sign-out are never refused, per §0 rule 2; the handset keeps anything refused queued and sends it after the
  update. The app shows one *Update the app* screen, with a store button once `field-app/src/release/stores.ts`
  holds the addresses. Every field-app response carries `X-Field-Schema-Version: 1`, which the handset reads into
  the change feed, so `sync/delta.ts` refuses a version it does not know.
* **The server is rolled back by its own rule** ("Revert the commit"), and a server revert that removes a field an
  installed build sends breaks the additive rule — so a server change on a field-app route is reverted only to a
  state the oldest supported build can still talk to.

### 5.4 · The first release itself

Rolling back the **whole** native app after launch means: halt both stores (§5.2), point the crew at the web field
app (still live), and leave installed handsets to send what they hold — the outbox is never purged unsent. Nothing
about the first release migrates server data, so there is nothing on the server to undo.

## 6 · The beta — one crew, one week, real work (T-59)

**Needs the going-live customer's people; the repository can only write the plan.**

| | |
|---|---|
| **Who** | One crew of the going-live utility: two to four field technicians, one meter reader with a real route, their supervisor, and one office contact who files reports. Named by the PO with the utility (§7) |
| **Handsets** | Their own issued devices, including **the cheapest one the utility issues** (T-52), at least one shared between two people (the shared-handset rules, Security §3), at least one tablet if they use tablets |
| **Build** | The production-profile binary from TestFlight (iOS: internal or external testers) and the Play **internal testing** track (Android) — the same binary that will be released, promoted rather than rebuilt |
| **Length** | Five consecutive working days of real work, not demo jobs. The web field app stays available as the fallback all week |
| **Before day 1** | Each person activates and signs in at the depot on wi-fi, the office confirms the menu reads the same `version · build` on every handset, and the crew is shown how to report (§4) |

**What to record every day** (the office contact, one row per person per day — a shared sheet is enough):

1. The `version · build` line from the menu (catches a handset that did not take an update).
2. Jobs completed and readings taken, **counted on the handset** (FF-35, RW-28) **and on the server** — the two
   must agree once the handset has been on wi-fi.
3. The sync number on FF-50 at the end of the day **after** depot wi-fi — it must reach 0. Anything refused, with
   its reason.
4. Hours spent without signal (roughly) and whether anything could not be done offline.
5. Battery left at the end of the shift.
6. Every fault, in the reporter's words, with the build line, filed the same day (§4), and the reply sent.
7. One sentence from each person: what slowed them down.

**Exit criteria — all of them, or the beta runs another week:**

* **No captured work lost.** Every item captured on a handset is on the server (accepted or duplicate) or visible as
  refused on the handset with a reason; nothing sits unsent for more than a day that had depot wi-fi in it.
* **No open defect that stops a job** being finished, and none on money (balance shown, stale-money warning, R16–R17).
* **Every reported defect has had a reply naming a build** (§4).
* **Crash reports checked by hand for customer data**, a sample of at least ten: no customer name, address,
  account, balance, reading, photo or signature (Security §7, item 5).
* **The crew's supervisor says they would rather keep it than go back** to the web field app.

**Stop the beta at once** if any captured work is lost or if a handset cannot open its day: the crew goes back to
the web field app, the binary's rollout stays at internal, and the fault is fixed before anyone tries again.
